# Doc Analyzer — 智能文档分析助手

## 概述

本技能提供一套结构化的文档分析框架，核心理念是**三阶渐进式分析**：

1. **全局速览**（30秒内建立认知地图）
2. **结构化提取**（按文档类型加载专属问题模板，定向萃取关键信息）
3. **深度追问**（引导用户基于提取结果进行决策级分析）

这个流程的设计意图是让人类做判断，让 AI 做苦力——AI 负责大量阅读和结构化提取，
人类负责在关键节点做出决策和追问。

---

## 环境准备

本技能的文档读取依赖 `doc-classifier` 的批量提取能力。如果需要处理 PDF、Word、
Excel、PPT 等非纯文本格式，请先确保 `doc-classifier` 的环境已就绪：

```bash
python <doc-classifier-skill-path>/scripts/batch_extract.py <文档路径> --output <doc-analyzer-skill-path>/tmp/extracted.json
```

**临时文件存储**：所有临时数据都将存储在 `doc-analyzer/tmp/` 目录下，该目录会自动创建。

如果文档已在上下文中（用户直接粘贴文本或上传了可直接阅读的文件），则无需运行脚本，
直接进入分析流程。

## 分析流程

### 第一阶：文档类型识别与全局速览

拿到文档后，首先快速判断文档类型。不同类型的文档有不同的分析模板和关注维度，
正确识别类型是高质量分析的前提。

根据文档的结构特征，将其归入以下类型之一：

| 文档类型 | 识别特征 | 问题模板文件 |
|---------|---------|-------------|
| 会议纪要 | 参会人员、议题、决议、待办 | `references/questions/meeting_minutes.md` |
| 领导讲话 | 讲话人、场合、指示/要求、引用 | `references/questions/leadership_speech.md` |
| 政策文件 | 发文机关、文号、条款、适用范围 | `references/questions/policy_document.md` |
| 工作报告 | 工作回顾、成绩、问题、计划 | `references/questions/work_report.md` |
| 方案规划 | 目标、路径、资源、里程碑 | `references/questions/plan_proposal.md` |
| 数据分析报告 | 数据指标、趋势、对比、归因 | `references/questions/data_analysis.md` |
| 通用文档 | 以上均不匹配时使用 | `references/questions/general.md` |

识别类型后，输出一段**全局速览**（不超过 5 句话），让用户在 30 秒内建立对文档的整体认知：

```
📄 文档类型：会议纪要
📅 时间：2025年1月6日
🏢 组织：ABC科技公司 产品研发部
📝 主题：Q1 产品规划与资源协调
📊 规模：全文约 3200 字，涉及 5 个议题、3 项决议、7 条待办
```

### 第二阶：结构化提取

根据识别的文档类型，**加载对应的问题模板文件**（在 `references/questions/` 目录下），
按模板中定义的维度逐一提取信息。

加载方式：使用 `view` 工具读取对应的模板文件，然后按其中的结构逐项提取。

```
# 示例：识别为会议纪要后
→ 读取 references/questions/meeting_minutes.md
→ 按模板中的"核心决议"、"待办任务"、"分歧与争议"等维度提取信息
→ 以结构化格式呈现给用户
```

输出格式遵循以下原则：用散文段落呈现分析内容，而非机械的问答对。每个维度用一段话
清晰阐述，重点信息加粗标注。如果某个维度在文档中未涉及，标注"文档未提及"而不是跳过。

### 第三阶：深度追问引导

结构化提取完成后，根据文档内容和类型，主动向用户提出 3-5 个有针对性的追问建议。
这些追问不是泛泛的"你还有什么问题"，而是基于文档内容推导出的、有决策价值的问题。

追问方向应覆盖以下层面：

**跨文档关联**：这个文档提到的某个问题，在其他文档中有没有后续？例如"上次会议遗留的
XX问题在本次会议中是否有推进？"

**优先级判断**：在文档列出的多项任务或问题中，哪些最可能是关键瓶颈？例如"文档提到的
5 项待办中，哪项对项目进度影响最大？"

**风险识别**：文档中哪些表述暗示了潜在风险？例如"方案中提到'视情况调整'的部分是否
存在不确定性风险？"

**行动推导**：基于文档内容，下一步应该做什么？例如"根据这份报告的数据趋势，
下个季度应该重点关注哪个指标？"

## 问题模板使用说明

所有问题模板存放在 `references/questions/` 目录下，每个模板文件包含以下结构：

```markdown
# [文档类型] 分析模板

## 模板说明
简要描述此类文档的特征和分析重点。

## 核心提取维度
按重要性排序的提取维度列表，每个维度附带提取指引。

## 输出格式模板
结构化输出的参考格式。

## 深度追问方向
针对此类文档的典型追问方向。
```

当用户分析同一类型的文档时，之前的分析中产生的有价值的追问会被追加保存到
对应模板文件的"用户历史追问"部分，形成持续积累的问题库。这使得每次分析都能
比上一次更精准地命中用户的关注点。

### 保存追问的方法

分析完成后，如果用户提出了有价值的追问（非模板预设的、体现了该用户独特关注点的问题），
使用 `scripts/save_questions.py` 将其持久化到对应的模板文件中：

```bash
# 保存单条追问
python <skill_path>/scripts/save_questions.py meeting_minutes "上次遗留的预算问题是否有推进？"

# 批量保存（用 | 分隔多条）
python <skill_path>/scripts/save_questions.py work_report "问题1|问题2|问题3"

# 查看某个模板的历史追问积累
python <skill_path>/scripts/save_questions.py meeting_minutes --list
```

脚本会自动去重（内容相同的追问不会重复保存）、添加时间戳，并追加到模板文件的
"用户历史追问"部分。下次分析同类文档时，`view` 加载模板文件时会自动包含这些历史追问。

**判断哪些追问值得保存**的标准：
具有复用价值（下次分析同类文档时仍然有意义）、体现了用户独特的关注维度（不是模板
已有的通用追问方向）、指向了决策需求（而非纯粹的好奇心）。

**如果技能目录是只读的**（如打包分发后未授予写权限），脚本会提示用户手动将追问复制
到模板文件末尾。这不影响分析功能本身，只影响追问的自动积累。

### 保存分析结果的方法

每次完成完整的三阶分析（全局速览 → 结构化提取 → 深度追问引导）后，使用
`scripts/save_analysis.py` 将分析结果持久化到 `references/history/` 目录中。
这样做的目的是：分析成果不随会话结束而丢失，可作为后续多文档联合分析的参考。

```bash
# 将分析结果写入临时文件，再保存（推荐，适合长文本）
python <skill_path>/scripts/save_analysis.py --type 会议纪要 --title "Q1产品规划讨论" --from-file <skill_path>/tmp/analysis_output.md

# 直接传入内容（适合短文本）
python <skill_path>/scripts/save_analysis.py --type 工作报告 --title "研发部年度总结" --content "分析内容..."

# 指定原始文档路径（可选，记录来源）
python <skill_path>/scripts/save_analysis.py --type 周例会 --title "Sprint回顾" --from-file /tmp/result.md --source /path/to/original.docx

# 查看历史记录
python <skill_path>/scripts/save_analysis.py --list
```

**何时保存**：在第三阶（深度追问引导）输出完成后，自动将第一阶和第二阶的分析内容
保存。具体步骤：
1. 将全局速览 + 结构化提取的结果写入 `<skill_path>/tmp/analysis_output.md`
2. 调用 `save_analysis.py` 保存到 `references/history/<当天日期>/` 目录
3. 脚本会自动去重（相同内容不会重复保存）、处理文件名冲突

**不需要保存的情况**：用户只是简单提问（没有走完整分析流程）、文档内容极短
（< 100 字）且分析价值有限、用户明确表示不需要保存。

## 多文档联合分析

当用户提供多个文档进行分析时（例如"帮我分析这三份会议纪要"），采用以下策略：

先对每个文档单独完成第一阶和第二阶分析，然后进入**联合分析模式**：

**纵向追踪**：按时间线串联多个文档，追踪同一议题在不同文档中的演变。
例如"XX问题从1月会议的'待讨论'变成了2月的'已决议'，中间发生了什么？"

**横向对比**：将同类文档放在一起对比差异。
例如"两份方案的核心差异在哪里？各自的优劣势是什么？"

**全局统计**：汇总多个文档中的任务、问题、决议，找出高频出现的主题。
例如"在这 5 份会议纪要中，哪些问题被反复提及但一直没有解决？"

## 输出规范

分析结果的呈现应遵循以下规范：

**文字密度**：全局速览控制在 5 句话以内。结构化提取的每个维度用 1-3 个段落阐述，
重点内容加粗。整体分析长度与文档复杂度成正比，但不应超过原文的三分之一。

**引用原文**：当涉及关键表述时（如领导讲话中的定性判断、政策文件中的具体条款），
用引号标注原文关键词，但不大段复制原文。

**不确定标注**：如果某个维度的信息在文档中不够明确或有多种解读，用"⚠️"标注
不确定性，并给出多种可能的解读。

**可操作性**：每次分析的最后一部分必须是可操作的——要么是追问建议，
要么是行动建议，要么是需要进一步确认的事项清单。

## 与 doc-classifier 的协作

`doc-analyzer` 和 `doc-classifier` 是互补的两个技能：

`doc-classifier` 解决"文件放到哪里"——它读取一批文件，按内容分类，归档到结构化目录。
`doc-analyzer` 解决"文件里说了什么"——它深入阅读单个或多个文件，提取要点，引导理解。

典型的协作流程是：先用 `doc-classifier` 把一堆混乱的文件整理好，用户通过生成的
INDEX.md 索引报告了解文档全貌，然后选择感兴趣的文档用 `doc-analyzer` 深入分析。

两个技能共享 `doc-classifier` 的批量提取脚本和 UV 虚拟环境，无需重复安装依赖。

## 边界情况处理

**加密/不可读文档**：如果文档无法读取（加密 PDF、损坏的 Word），告知用户文档无法解析，
建议他们先解密或修复文档后重新提供。

**极短文档（< 100 字）**：仍然走完整分析流程，但全局速览和结构化提取可以合并为一段简短
的分析。追问部分改为"基于有限信息的推断性提问"。

**极长文档（> 20000 字）**：优先分析文档的开头（摘要/引言）、小标题结构和结尾（结论/建议），
中间部分按小标题跳读。告知用户分析基于关键段落而非全文逐字阅读。

**多语言文档**：自动适配文档语言输出分析结果。如果文档是英文，分析结果默认也用英文，
除非用户明确要求使用中文分析。

**表格/数据密集型文档**：如果文档以表格数据为主（如 CSV 或 Excel 导出），自动切换到
数据分析报告模板，即使文档不是严格意义上的"分析报告"。

**已分类的文档**：如果用户通过 `doc-classifier` 归档后选择某个文件分析，可以利用
分类信息（文件路径中的类别名）来辅助判断文档类型，提高类型识别的准确率。

    ├── questions/                        # 问题模板库
    │   ├── meeting_minutes.md            # 会议纪要

## 核心原则

分析的目标是帮助用户**理解**文档，而非**复述**文档。每次分析必须以可操作的输出结尾——追问建议、行动建议或待确认事项。拿不准的信息用 ⚠️ 标注，不做确定性的错误判断。模板是指引而非枷锁，实际分析应根据文档内容灵活调整提取维度。
